# Demand Hypothesis

## Definition

A demand hypothesis is a **falsifiable prediction** derived from one or more supported PULL patterns.

It predicts that a defined class of actors, in a defined situation, will commit scarce resources toward a Project within a defined time window because their current options fail a particular acceptance boundary.

This term is an extension used by this repository. It is intentionally distinct from Snyder's earlier "PULL hypothesis" terminology. Snyder's September 2026 essay argues that teams should not invent PULL hypotheses before finding real PULL anecdotes:
https://thephysicsofstartups.substack.com/p/no-more-pull-hypotheses

Our use of **demand hypothesis** occurs downstream of anecdotes and patterns:

```text
PULL anecdote → PULL pattern → demand hypothesis
```

## Required fields

### Actor / segment
Who is predicted to exhibit the demand, and in what relevant state?

### Project
What product-agnostic outcome are they trying to produce?

### Forcing condition and window
Why does this become active now, and by when must it be addressed?

### Existing commitment
What scarce resources should already be moving before our supply appears?

### Current option set
What do they actually use or seriously evaluate?

### Blocking limitations
Why do those options become inadequate under the relevant constraints?

### Transaction path
How can intent become a purchase, pilot, hire, implementation, or other allocation?

### Acceptance boundary
What must a new option accomplish to become viable?

### Observable next commitment
What behavior should occur if the hypothesis is correct?

### Falsification condition
What evidence would materially weaken or reject it?

### Revalidation condition
When should the hypothesis be reconsidered because the environment has changed?

## Canonical statement

> **As of [date], we hypothesize that [actor/segment in a defined state] needs to accomplish [Project] by [time boundary] because [forcing condition]. Before our supply appears, they are already committing [resources] and using or evaluating [options]. Those options fail under [constraints] because [limitations]. A viable new option must [acceptance boundary]. Resources can be committed through [transaction path]. If this demand is real and repeatable, we expect [next commitment] by [date/event]. We should weaken or reject the hypothesis if [falsification condition].**

## Why commitment precedes budget

A defined budget can exist without an active buying motion.

The stronger question is:

> What is the actor already sacrificing because this Project matters?

A credible demand hypothesis should usually predict some pre-existing commitment of money, time, labor, attention, political capital, or implementation effort even before the proposed supply exists.

## Demand hypothesis vs product hypothesis

A demand hypothesis predicts customer state and behavior.

A product hypothesis predicts that a particular supply will cross the acceptance boundary.

Keep them separate.

Example:

**Demand hypothesis**
> Teams facing a renewal deadline will allocate resources to eliminate a manual compliance bottleneck.

**Product hypothesis**
> An automated evidence-collection workflow can remove that bottleneck sufficiently to trigger a paid pilot.

Separating these prevents failure of one product implementation from being mistaken for absence of demand.
