# Concepts, lineage, and extensions

## Intellectual lineage

This repository builds on Rob Snyder's PULL framework.

Snyder describes PULL as a state in which a person has:
- a **Project** on their to-do list;
- a situation making that project **Unavoidable** now;
- a **List** of available options;
- **Limitations** in those options that prevent adequate progress.

Snyder emphasizes that the Project is product-agnostic and that the available options are broader than direct competitors. He also distinguishes actual pull from enthusiasm or positive feedback.

In September 2026, Snyder explicitly argued for replacing a guessed "PULL hypothesis" with a **PULL anecdote**: one real person exhibiting real PULL now. His concern was that hypothesis-first reasoning makes it easy for founders to invent a plausible story and then interpret subsequent evidence in its favor.

## Repository-specific extensions

The concepts below are extensions developed here for operational analysis. They should not be attributed to Snyder unless a source explicitly supports them.

### Terminology note: "PULL hypothesis"

This repository does **not** use `PULL hypothesis` as a current artifact type.

Snyder used the term historically and later argued for starting from real PULL anecdotes instead of invented PULL hypotheses. If an incoming note or teammate uses "PULL hypothesis," normalize the intended meaning to one of:

- **candidate PULL pattern** — if it means "we think this structure may recur"; or
- **demand hypothesis** — if it makes a predictive claim about future resource commitment.

Do not create a fourth object merely because the phrase appears in source material.

### PULL anecdote

A time-stamped record of one real actor exhibiting, or potentially exhibiting, PULL.

It is descriptive before inferential.

### PULL pattern

A recurring structure across multiple independent PULL anecdotes.

A pattern describes what appears to recur. It does **not** yet claim that the recurrence will generalize.

### Demand hypothesis

A falsifiable prediction that actors in a defined state will commit scarce resources toward an outcome within a defined window when their current options fail a particular acceptance boundary.

A demand hypothesis is inferred from evidence. It is not itself evidence.

### Forcing condition

The event, constraint, or state that makes the Project difficult to defer.

This operationalizes the time-specific nature of Snyder's "Unavoidable" dimension.

### Existing commitment

Resources the actor is already spending, reallocating, or risking because the Project matters.

This can include money, time, headcount, attention, political capital, procurement effort, workflow disruption, or implementation work.

A budget can support a demand claim, but **budget existence and commitment are not the same thing**.

### Transaction path

The mechanism by which current intent can become an actual allocation of resources: discretionary budget, procurement, pilot approval, contractor replacement, headcount tradeoff, executive exception, or another route.

### Acceptance boundary

The conditions a new option must meet to become viable.

This is not a feature list. It is the boundary between an option that remains inadequate and one that can plausibly unblock the Project.

### Observable next commitment

A predicted action that should occur next if the inferred demand is real.

It should be costly enough—in money, time, coordination, risk, or political capital—that it discriminates better than verbal enthusiasm.

## Core epistemic chain

```text
observation → anecdote → pattern → demand hypothesis → test → new observation
```

At every arrow, information is lost and inference is added. The agent must make those transitions explicit.
