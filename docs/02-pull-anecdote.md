# PULL Anecdote

## Purpose

Capture one real instance of customer PULL, or a possible instance, without prematurely generalizing it.

Snyder's September 2026 "No more PULL hypotheses" essay motivates starting from a real anecdote rather than from a guessed market hypothesis:
https://thephysicsofstartups.substack.com/p/no-more-pull-hypotheses

## Unit of analysis

One anecdote = **one actor + one Project + one active time window**.

Do not create multiple anecdotes from multiple quotes about the same underlying episode.

If several actors are involved in one buying process, preserve both:
- the individual actor perspective;
- the shared organizational episode identifier.

That makes it possible to avoid counting one buying event as several independent cases.

## Required fields

### Identity and provenance
- anecdote ID;
- actor ID;
- episode ID where relevant;
- source IDs;
- observed date;
- source channel;
- collection method;
- whether the source was solicited because it looked promising.

### Actor state
- role;
- organization/context;
- relevant constraints;
- relationship to the Project;
- relationship to the transaction.

### Project
What outcome is the actor trying to accomplish?

The Project should be product-agnostic.

### Forcing condition and window
- Why now?
- By when?
- What changed?
- What happens if they wait?

### Existing commitment
What scarce resources are already being consumed or put at risk?

### Current option set
For each serious option:
- actually used;
- actively evaluated;
- considered but rejected;
- merely mentioned;
- not considered / unknown.

Include doing nothing and delay where relevant.

### Blocking limitations
For each serious option:
- what prevents it from adequately accomplishing the Project;
- why that limitation matters in this time window;
- evidence supporting the claim.

### Transaction path
- approver/economic buyer;
- funding or resource source;
- procurement/approval steps;
- switching or implementation requirements;
- known blockers.

Unknowns should stay unknown.

### Acceptance boundary
What would have to become true for a new option to be viable?

### Observable next commitment
What behavior should happen next if the PULL persists?

### Counterevidence
Record evidence that weakens the PULL interpretation:
- low urgency;
- adequate incumbent option;
- repeated delay;
- inability/unwillingness to allocate resources;
- contradictory statements;
- stalled transaction;
- disappearance of the forcing condition.

## Canonical statement

> As of **[date]**, **[real actor]** is trying to accomplish **[Project]** by **[time boundary]** because **[forcing condition]**. They are already committing **[resources]** and are using or actively evaluating **[options]**. Those options are inadequate under the current constraints because **[limitations]**. A viable new option would need to **[acceptance boundary]**. If the inferred PULL is real and persists, we expect **[observable next commitment]** by **[date/event]**.

This statement is a compression of the evidence, not a substitute for it.
