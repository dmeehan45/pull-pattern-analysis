# PULL Pattern

## Definition

A PULL pattern is a recurring structure across multiple **independent** PULL anecdotes.

It is descriptive:

> Under these observed conditions, these elements appear to recur.

It is not yet predictive:

> People like this will behave this way in future cases.

The latter belongs in a demand hypothesis.

## Pattern fields

A candidate pattern should identify recurring:
- actor state;
- Project;
- forcing condition;
- active time window;
- commitment behavior;
- option set;
- blocking limitations;
- transaction path;
- acceptance boundary;
- next commitment behavior.

It must also identify:
- variation;
- counterexamples;
- dependent cases;
- sampling limitations;
- cases that nearly fit but fail in one important dimension.

## Pattern states

Use qualitative states rather than a pseudo-precise numeric score:

- **candidate** — a possible recurrence is visible;
- **challenged** — active falsification work is underway;
- **supported** — the pattern has survived meaningful attempts to disconfirm it across independent cases;
- **split** — evidence suggests the original pattern combines two or more materially different patterns;
- **rejected** — counterevidence or a better explanation defeats it;
- **stale** — it may have held previously but requires revalidation.

"Supported" does not mean proven.

## Pattern boundaries matter

Do not average away meaningful differences.

If two groups share the same Project but have different:
- forcing conditions,
- commitment behavior,
- transaction paths,
- acceptance boundaries,
- or next buying actions,

they may be separate patterns.

A narrower pattern that survives falsification is more useful than a broad pattern that merely sounds intuitive.

## Required adversarial comparison

Before promoting a pattern, compare at least four buckets when available:

1. clear apparent PULL;
2. weak/ambiguous PULL;
3. negative cases where the Project exists but no buying motion occurs;
4. cases where a transaction occurred for a materially different reason.

The comparison should answer:

> What separates the cases that pull from the cases that do not?

## Independence check

Raw anecdote count is not enough.

Ask whether supporting cases:
- come from different organizations;
- come through different acquisition channels;
- share the same referrer;
- arise from the same market shock;
- reflect the same internal buying event;
- were selected because they already bought.

Record these dependencies explicitly.

## Pattern statement template

> Across **[independent case set]**, actors in **[state]** repeatedly activate **[Project]** when **[forcing condition]** occurs. They commit **[resources]**, consider/use **[options]**, and encounter **[limitations]**. The pattern appears to hold when **[boundary conditions]** and fails or weakens when **[negative conditions]**. The highest-risk alternative explanation is **[rival explanation]**.

A candidate pattern should always travel with its strongest rival explanation.
